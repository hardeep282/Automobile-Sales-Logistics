# Audit log: v1 → v2 (November 2026)

A full review of the v1 repository (SQL, notebooks, Streamlit app, Power BI model). Each finding lists the evidence, the fix, and the effect on reported numbers. The v1 code is still in git history (commit `42bcece`).

## A. Deployment

| # | Finding | Evidence | Fix |
|---|---|---|---|
| A1 | The live Streamlit app couldn't find its data on Linux | `app.py` read `data/Cleaned-Data/…` but the folder was `Data/`. Windows ignores case; Streamlit Cloud (Linux) doesn't | Folder is now lowercase `data/`. Paths are built from `Path(__file__)` |
| A2 | Dependency install failed on Linux | `requirements.txt` was a 120-package Jupyter `pip freeze` including `pywinpty` (Windows-only), saved with a BOM | Lean `requirements.txt` (4 packages) for the app; `requirements-dev.txt` for analysis |
| A3 | Notebooks only ran on one laptop | hard-coded `C:/Projects/...` paths; outputs written to a git-ignored folder; `yellowbrick`/`tabulate` imported but not in requirements | Notebooks import a tested package with relative paths. Figures are regenerated by `scripts/run_pipeline.py` |

## B. SQL

| # | Finding | Evidence | Fix | Effect |
|---|---|---|---|---|
| B1 | **Script left the database in the double-counting state** | `gold_ops_productline_month` was created (referencing the bridge before it existed), then dropped and recreated *without* the allocation | Numbered scripts, `CREATE OR ALTER` in dependency order | Clean run on a fresh DB |
| B2 | **Product-line revenue allocated 1/n** | bridge weight = 1 ÷ product lines in the order, although each line has its own `SALES` | Sum line-level sales | Trains +138% → corrected; Planes −25% → corrected; Vintage Cars 2.12M → **1.81M**; Classic Cars 3.55M → **3.84M** |
| B3 | IN PROCESS counted as "stuck" | all 41 lines dated 29–31 May 2020 (last 3 days) | Status group *Open*, excluded from rates | Revenue at risk 590k → **251k** |
| B4 | Lost and at-risk revenue mixed together | CANCELLED revenue counted as "at risk" | Separate *Revenue Lost* KPI | £194k lost reported on its own |
| B5 | Two different "high risk" definitions | `gold_orders` (excl. IN PROCESS) vs `gold_order_ops_fact` (incl.) | One mapping: `silver.ref_order_status` | Consistent KPIs everywhere |
| B6 | RESOLVED status ignored | not in any flag | Fulfilled + `had_issue` | Issue rate KPI |
| B7 | "Profit proxy" mislabelled | `(MSRP − price) × qty`; 51% of lines sell above MSRP; no cost data | Renamed price realisation vs list | Honest metric |
| B8 | MoM growth compared non-adjacent months | `LAG` over existing rows only | Calendar-month spine | Correct growth |
| B9 | Country rates without sample size | Sweden/Denmark 14.3% = 1 of 7 orders | `low_sample_flag`, *failed / total* shown | No over-reading |
| B10 | No tests, exploration mixed with DDL | one 860-line file | `05_data_quality_tests.sql` (23 tests) + CI running the SQL in DuckDB | Reproducible |

## C. Python analytics

| # | Finding | Evidence | Fix | Effect |
|---|---|---|---|---|
| C1 | **RFM F and M scores inverted** | rank `ascending=False` then labels `[1,2,3,4]`; Euro Shopping Channel (26 orders, top customer) = F1 M1 = *Low Value*; "Low Value" averaged £151k vs "High Value" £62k | Percentile-rank scoring, higher = better; unit tests on direction | High tier: 22 customers, **46%** of revenue, avg £202k |
| C2 | Ties scored arbitrarily | `rank(method="first")` | `method="average"` | Same value → same score |
| C3 | **K-Means labels didn't match the clusters** | cluster with 2-day recency & £784k avg named "Dormant / At Risk"; a second notebook used a different name map | Labels generated from cluster medians | Labels can't drift |
| C4 | k = 4 without evidence | code comment "how number of clusters were decided?" | Silhouette over k = 2..8 → k = 4 (0.45) | Justified |
| C5 | Skewed features with MinMax scaling | two accounts = 16% of revenue | log-transform + standardise | Stable clusters |
| C6 | **Regression R² = 0.971 overstated** | revenue = orders × AOV (near-identity); 18-row test split; unscaled coefficients ranked as "impact"; reliability effect +£3k against £23k RMSE | log-log OLS, HC3 robust SE, 95% CIs, 100-fit repeated CV, outlier sensitivity | Elasticity **1.06** (0.82–1.31); fulfilment-issue effect **p = 0.68** (not significant, low power: 10/89 customers) |
| C7 | Arbitrary shipping % buckets | 82% "Reliable" from thresholds 0.70/0.85/0.95 | Event-based fulfilment experience | 77 clean · 10 at risk/lost · 2 resolved |

## D. Power BI

| # | Finding | Fix |
|---|---|---|
| D1 | **`DimDate` had no relationships**: every YearMonth slicer did nothing; YTD / MoM / YoY returned the overall total | Calculated `dim_date` marked as the date table, related to the fact |
| D2 | Auto date/time on (3 hidden LocalDateTables) | Turned off |
| D3 | Aggregated `gold_ops_country_kpis` used as the country dimension | Proper `dim_country` |
| D4 | Bidirectional bridge → fact relationship | Star schema, single direction |
| D5 | Allocated-revenue measures (1/n) | Exact `[Total Revenue]` by product line |
| D6 | `Product High Risk % Fresh` referenced the non-"Fresh" base measure; leftover duplicates | Measures rebuilt in folders with descriptions |
| D7 | Data source hard-coded `.\SQLEXPRESS` in each query | `ServerName` / `DatabaseName` parameters |
| D8 | Binary `.pbix`, no diffs | PBIP: TMDL model + PBIR report, schema-validated |

## Unchanged

Total revenue (£9,760,221.71), order count (298) and failure rate (2.35%) are the same in v1 and v2, which confirms the raw data was read correctly in both.
